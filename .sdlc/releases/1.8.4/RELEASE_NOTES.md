# Release 1.8.4

**Date:** 2026-10-23
**Previous:** v1.8.3

## Highlights

Fixes the opt-in screen, which subscribed nobody, and the settings notice, which couldn't be dismissed. Takes free_plugin_lib 1.3.3, and loads the
Google Maps API through WordPress's script loader so the plugin passes Plugin Check.

## What's New

### Fixes
- "Allow & Continue" on the opt-in screen subscribed nobody and recorded the user as opted out; it now subscribes.
- The settings notice could not be dismissed and came back on every page load.
- On sites running other Fullworks free plugins, the opt-in notice and menu could belong to the wrong plugin.
- Until the user chooses Allow or Skip, the plugin's settings page now shows the opt-in screen.
- Deleting the plugin removes the opt-in status it stored (new uninstall.php).

### Improvements
- The notice links straight to the opt-in screen.
- The Google Maps API loads through wp_enqueue_script in the footer, once per API key instead of once per map.
- Tested up to WordPress 7.1; bundled opt-in library 1.3.3; translation template regenerated.

## Breaking Changes

None intended. Map scripts now print in the page footer rather than next to each map. Maps rendered after the footer, or
in AJAX or REST responses, still print their script inline as before.

## Migration Guide

None. Users stored as opted out under the old bug stay opted out (Alan's decision, PLUGINS_SMALL-7).

### Verification of the script-loading change (no ticket, so recorded here)
Checked in wp-env (WP 7.1.3), in a block theme (Twenty Twenty-Five) and a classic theme (Twenty Twenty-One, plus a map in a
text widget), on pages with one map, three maps, and two maps with different keys:
- Map container HTML (normalising the random map id) is **identical** before and after on all 6 page and theme combinations.
- API scripts. Before: one per map, so 3 maps loaded the API 3 times and the widget page 4 times. After: exactly one per key, in
  the footer, each followed by its maps' init code.
- Headless Chrome with a stubbed `google.maps` (served via script_loader_src): every map was constructed against its own
  container with the right zoom and markers (for example, three maps produced 3 maps and 4 markers).
- Late paths: an AJAX-rendered pair of maps printed the API script once, then both inits; a map rendered on `wp_footer`
  at priority 100, after the footer scripts, loaded its key and initialised.
- No PHP notices (debug.log stayed empty). Plugin Check (wp-env, real slug): 0 errors.
- Known and unchanged: two different API keys on one page load the Google API twice, which Google rejects, as before.
